# 图片拒绝后的冷却重试

2026-10-29 最新用户明确取消剩余 LOW 的全部项目冷却，并要求立即入队。[固定17项授权](../data/retry-cooldown-waivers/20261029-remaining-low-immediate.json)由策略SHA绑定；这些来源后续的合规原请求重试采用零等待，覆盖下文默认8小时。原拒绝回执、原8小时截止、已用次数完整保留，新的有效截止不会伪装成原等待已经过去。仍须原词、原输入字节/顺序/透明参数、同一内置工具、实际请求及工具允许，累计上限不增加。HIGH 跳过规则不变。14个服务等待项立即具备时间准入；2个受保护原图和1个已返回网络错误也登记在[完整17项用户队列](../data/production-user-queues/20261029-remaining-low-immediate.json)，其准入问题不能冒充已调用或已完成。

2026-10-24 用户针对当时已经耗尽的31个HIGH明确要求“再给我试一轮”。[固定授权与31项原始证据](../data/extra-retry-rounds/20261024-exhausted-high-31-one-more.json)给这些来源各追加一次累计冷却重试，即8→9；其他来源仍为8，后来才达到上限的来源不自动加入。本轮仍保持每次拒绝后至少8小时、同一内置工具、完整原prompt、相同有序输入字节和工具参数、允许原请求与工具重试、返回图片即停止。次数不清零，第9次仍拒绝则该额外一轮耗尽，不能自动再追加。

默认上限仍为2026-10-18用户明确的 **8 次重试**，覆盖原先的一次及中间提出的四次。初次调用不计入重试；下文八次默认规则结合上述固定31项明确例外执行。次数不因改规则、换批次或已接受结果的美术返修而清零。

每次真实服务拒绝之后，从可靠 UTC 回执重新计算至少八小时。到期且原请求仍允许、工具也允许重试时，保持完整实际 prompt、输入字节、输入顺序、透明背景参数及同一内置工具；实际调用前持久化消耗一次额度。服务返回图片即停止该请求的冷却重试，随后单独审图；第八次重试仍拒绝则停止自动重试。结果未知的调用先核对，不重复提交。非服务拒绝错误不能直接作为自动冷却重试依据。

`data/image-retry-policy.json` 是版本化参数，`tools/image_retries.py` 强制逐次冷却、八次累计上限、原词/输入链一致及成功停止。唯一生成执行者在导入间隙调用 `sync`，迁移旧的“已用完一次”状态，保留历史状态补注与已用次数，并以最近一次拒绝重新计算截止；审查者不并发改写共享队列。历史已成功但后来发生独立美术返修拒绝时，保留旧成功记录，以新拒绝原请求进入同一个来源累计预算。

固定额外一轮由策略中的 `source_scoped_extra_retry_rounds` 精确列出来源，绑定不可变授权清单SHA。`retry_limits.py`给被选来源9、其他来源8，拒绝同一来源静默叠加额外轮次；加载策略时核验原清单完整字节和31项身份。唯一执行者在无调用的空闲边界一次性同步变化后的来源上限，随后只读到期探针才可发现这些项；同步前后已用次数逐项相等，原8小时下限不缩短。第9次请求在调用前同时保存授权ID/清单SHA，dispatch再次核对；请求内容和输入不因追加额度改变。旧审核字节完全一致才可复用，缺失当前审核要求或证据先补审，不能把追加额度当作内容批准。

本次31项额外一轮已实际全部执行，[逐项审计](../data/extra-retry-rounds/20261024-exhausted-high-31-completed.json)为31次服务拒绝、0张PNG、0次其他错误，实际客户端最多1路。每项累计已用9，额外一次均已消耗；没有依据追加授权再发第10次。75项实际检查及后续20项聚焦检查的[记录](../data/extra-retry-rounds/20261024-exhausted-high-31-validation.json)与真实服务结果分开，测试输出中的模拟quota不计入生产进度。

调度将已经实际审阅原输入和完整提示词的到期 HIGH 请求，插入单路新图批次之间。每轮都核对最近失败调用的实际 UTF-8 参数快照、prompt SHA、输入 SHA、透明背景参数和截止；只有字节完全一致才能复用先前的内容审阅。冷却时继续生成其他高优先级人物。HIGH 冷却或额度耗尽不代表完成，不解锁 LOW。

统计按不同原始 SHA 去重；“第 n 次重试成功”仅指第 n 次冷却服务调用实际返回图片，不能拿后续美术修订次数代替。调用前已领取但尚未返回的请求单列，不能算失败或成功。既有统计快照保留原观察时间；`data/retry-statistics/` 中的机器 ID 和 UTC 只证明该次本机读回。

重试请求有意保持相同字节，因此不同轮次的完整请求快照可能有相同 SHA。实际 attempt 归属必须同时按唯一 dispatch 中的来源、attempt 编号、机器身份、快照完整路径及 SHA 绑定，不能只用 payload SHA 从 journal 反查唯一项。`production_queue.attempt_for_snapshot` 执行这一检查。第二轮 cooldown-011 暴露了原归档代码仅按 SHA 匹配的缺陷；修正后从已经实际返回的十二条调用记录完成归档，没有再发图像请求或再消耗次数。实际六次出图、六次拒绝见该批回执；美术批准仍分开记录。

本次规则变更的本地验证包含连续八轮、每轮截止前一秒拒绝领取、旧一次额度迁移、成功停止、输入链改变拒绝，以及原提示词/输入保真。测试不产生图片或费用，也不将模拟八轮冒充已执行的服务重试。真实第二至第八轮结果必须等待实际返回后记录。
