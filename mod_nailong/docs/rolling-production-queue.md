# 单路生成与审图重叠

用户指出审图可以与下一张生成重叠。此前几次把整批审图、记录和提交串在两批调用之间，造成可避免的队列空档；约 18 张合格图/墙钟小时的历史均值包含这些空档，不能解释为内置图片工具的硬上限。旧时间预测保留在历史记录，新安排以实际测量继续修正。

保持一条内置图片生成通道，提前备好原图和已经落盘的实际 prompt。返回一张后立即导入，处理已排队的审图决定，再派发下一张；在该调用进行时审查上一批已返回图并准备后续输入。审查者只写小型决定文件，不同时重写 `generated.json`；同一个生成执行者在两次调用之间应用决定，避免审查覆盖刚导入的其他图片。

`production_queue.py begin` 核对冻结 prompt / 输入 SHA 并独占记录实际调用，已有调用或未知结果阻止重复派发。`returned` 记录实际返回文件或错误。`review` 接收人工审图的来源 SHA、当前输出 SHA、attempt 与对照页证据 SHA，只排队；`apply-reviews` 在生成执行者边界重新核验后批准或驳回。旧图被替换、attempt 已变化的决定标为 stale，不应用到新版。自动化本身不产生美术批准。

Windows 的跨进程 prompt 传输必须使用 `export-job` 的 ASCII 转义 JSON。执行器保存实际将发送的完整 job 后，用 `begin --actual-job-file <快照>` 校验，不能只校验原始 job 文件。法国首批 17 次历史偏差、真实调用词恢复及记录边界见[传输更正](prompt-transport-correction-015.md)；该偏差不应再次发生。

2026-10-17 的[实测回执](../data/review-generation-overlap.json)绑定 `machine_id: bf-202609141645-5434332d4d`：下一张 HIGH 原图调用从 15:26:39.936 到 15:27:29.361 UTC，期间于 15:27:05 写入五张已实际审查图的决定，执行者在新图导入后于 15:27:30 应用，且保留新图。证明决定记录与生成实际重叠；不把这条 49.424 秒的含工具传输间隔声称为服务端纯生成时长、持续产能或上限。页面观看本身的全部用时没有单独计时。

流水线稳定后的每张周期接近 `max(生成时间, 该通道外所需的准备与审图时间) + 必要导入/派发开销`，而非机械相加。审图较慢、准备队列耗尽或同步记录冲突仍会产生瓶颈；美术返修与服务拒绝也会消耗调用或影响合格数量。不能宣称任何情况下审图都绝无影响，也不能继续把可避免的串行空档算作生成工具本身的限制。高清归档可作为另一项文件传输任务重叠执行，不占图片生成通道。

2026-10-18 更新：高清原始 PNG 已改为直接进入普通 Git。远端验证从固定 commit 读取索引、生成记录和真实 Git blob，允许工作树在此期间继续导入下一张；旧的完整下载证据只在远端 blob、路径、大小都完全相同时复用，保留原下载时间与 commit。`master_git_remote.py` 不再依赖正在变化的工作树来定义核验范围。

在必要的提交检查期间，执行器先派发一路内置调用，同时由单一 checkpoint 写入者整理索引、审查记录、构建并冻结本地 Git commit。返回图片或错误先保存实际回执，导入/失败记录等待本地提交完成，避免共享 JSON 被交叉覆盖。完成本地提交后立即恢复导入和下一张派发；推送固定 commit 与 PNG 远端读回作为有限的独立文件传输任务继续运行，不再让生成通道等待网络。只用普通 fast-forward push，将已冻结的 commit 推到 master；推送和核验成功分别以实际回执为准，不能把本地提交写成已推送。后台任务的失败必须读回并处理，不能随生成调度一起遗忘。
